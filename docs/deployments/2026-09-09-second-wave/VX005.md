# VX005 minimum recovery slice

## CURRENTLY VERIFIED

`scripts/cleanup_stuck_docs.py` now treats `processing` as diagnostic-only.
`--dry-run` counts both `failed` and `processing` entries without constructing
LightRAG or modifying `kv_store_doc_status.json`. It is an aggregate diagnostic:
it emits a count and does not add a document-ID list.

An invocation that identifies a failed document (`--all-failed` with at least
one failed entry, or `--hash` for a failed document) returns exit code 1 with
`pipeline_lock_unshared`. It does not construct RAG or call
`adelete_by_doc_id`. A `processing` hash is rejected with
`processing_not_eligible`. If `--all-failed` finds only `processing` entries,
it returns exit code 0 with `docs_identified=0`, `docs_deleted=0`, and a
`processing_not_eligible` report entry: this means no eligible failed document,
not successful deletion. No original source material is deleted by this slice.
For `--hash`, a non-dictionary status entry is rejected with exit code 1 and
`invalid_status_entry`; the report uses the fixed status `invalid` and never
echoes the malformed value.

The verified command was:

```sh
OMNIGRAPH_LOAD_ENV=0 .venv/bin/python -m pytest \
  tests/unit/test_cleanup_stuck_docs.py \
  tests/unit/test_ingest_prestart_read_only.py -q
```

It passed `16` tests. The test fixtures use pytest temporary directories and
mock the write seam. `test_ingest_prestart_is_a_read_only_status_report`
confirms the systemd pre-start commands remain `cleanup_stuck_docs.py --dry-run`
and do not construct RAG.

## Deployment boundary

This candidate must not be deployed in the current phase. Any still-active
unit that invokes `cleanup_stuck_docs.py --all-failed` would receive its
non-zero fail-closed result and could block its unit startup. The candidate
cannot be released alone: deployment requires a reviewed, coordinated systemd
template that retains the read-only `cleanup_stuck_docs.py --dry-run`
pre-start contract. The current slice performs no deployment.

## NOT ACCEPTED

VX005 does not establish cleanup-to-pipeline mutual exclusion. A cleanup-only
`flock` would serialize two cleanup commands but would not stop
`batch_ingest_from_spider.py` or any other ingest writer; it is therefore not
evidence that deleting a failed document is safe. No two-process shared-lock
acceptance claim is made here.

## Exact required scope extension

Before re-enabling deletion, change the actual RAG writer entry points to
acquire the same non-blocking, storage-local lock for their full write window:

1. `batch_ingest_from_spider.py` must acquire the lock before creating or using
   the shared RAG instance and release it only after its ingest/finalization
   writes complete.
2. Trace and include every other production entry point that can call
   `ingest_wechat.get_rag()` followed by `ainsert` or `adelete_by_doc_id`; a
   partial writer list is insufficient.
3. `scripts/cleanup_stuck_docs.py` may attempt that same lock non-blockingly.
   On contention it must return a machine-readable busy result and make no RAG
   call.
4. Add a real two-process fixture: one process holds the shared writer lock
   while a second process runs cleanup, demonstrating refusal; then reverse the
   order and demonstrate the writer refuses. The fixture must use a temporary
   storage directory and real OS locking, not mocked lock acquisition.

This expansion would require the batch-orchestration regressions named in
`AGENTS.md`, including `tests/unit/test_ingest_from_db_orchestration.py` and
the matching `_ingest_fixtures.py` schema checks. It is not implemented in
this VX005 slice.
