# VitaX 三模块整改规格

日期：2026-10-02。状态：**proposed / ready-for-review，待执行**。本规格依据三子代理核查及用户对本地完整文章阅读的澄清；不构成本轮生产变更授权。

## Problem Statement

维护者需要每天有资料进入可读文章库，并持续获得有来源的知识、Wiki与关系。当前旧链有产出，新网页也有本地验收，但两者之间缺少完整交接：初始化限流、失败记录不能按reconcile承诺重入、部分来源长期失效、图/KV副本过旧、Wiki建议未消费，本地阅读又被ingest-ok与公开accepted门共同限制。

2026-10-02核查快照：2958篇已有正文，其中1562篇无对应成功ingestion；1437个成功来源中18个未进1419来源/1447修订的旧候选；新站只读7条文章解读和2篇Wiki。上述计数是审计固定点，执行时按来源ID和当次快照重新对账。

## Solution

保留一套采集和处理链、一套VitaX网页/HTTP入口。维护者本地通过显式配置的只读文章数据库浏览原文、已有译文和缺失状态；公开站继续读取已接受知识release。已有资料可阅读与知识加工成功分开验收，公开资格不自动扩张。

先并行解除生产入口阻塞和贯通本地阅读；再分别收口来源覆盖、存储副本、Wiki实质更新；补上已存正文到现有知识生产入口的最小桥接。复用既有公开接受、builder、单云发布与日更票，最后验证同一条来源从采集到本地可读、知识接受与公开可读的闭环。

## User Stories

1. 作为维护者，我能浏览已抓文章，包括尚未建图成功或未获公开资格的文章。
2. 我能按来源、标题、原文及已有译文搜索文章，并翻页到全部匹配记录。
3. 我能打开原文和已有译文；正文或译文缺失时看到准确状态，不自动调用模型补写。
4. 我能区分原文章、文章解读和Wiki，避免把知识条目数理解成文章总数。
5. 我能看到实际输入快照时间和缺失清单，不把旧候选当最新全库。
6. 指定信息源在约定周期内有可对账的扫描尝试，零新增和失败也有记录。
7. RSS源抓取、正文获取、分类与ingestion分别报告实际成功和部分失败。
8. ingestion完成初始化、处理候选并持久化；明确申请重试的失败记录最多消费一次请求。
9. 图、正文KV、chunks和所选向量副本来自一次一致快照；修改/删除有明确交接语义。
10. Wiki建议产生有来源的实质正文变化，并可证明应用和幂等；占位页不算完成。
11. 新公开知识复用既有文章，严格保留引用、语言和已接受基线；原文/译文不因此公开。
12. 新来源经既有生产入口成为文章解读，再由至少两个不同来源支撑Wiki。
13. 手工发布成功后，既有单调度在08:00 Asia/Shanghai提升验证成功的版本；失败继续服务前版。

## Implementation Decisions

### A. 状态与输入权威

- “抓到记录”“正文可读”“分类通过”“ingestion完成”“Wiki已应用”“公开accepted”“release已服务”是不同状态；任何前一状态不自动证明后一状态。
- 暂由当前pipeline数据库提供最新文章事实，Hermes/vault是既有镜像；本阶段不迁移生产主写者。PC单写及旧链退役沿既有最终切换票。
- 本地文章输入必须是一份明确的完整SQLite输入，优先已有完整镜像；若Mac仅有成功子集，通过已授权SSH及SQLite一致备份/已用allowlist导出获得源码外私有副本，**不按ingest-ok筛选**。
- API响应只暴露文章所需字段。账户、凭据、任务日志及未知表不成为网页数据；不把完整库或记录交给子代理提示词。
- 本地读取直接使用该库，不先扩大全量候选JSON导入。旧1419/1447保全候选继续保留，不重新迁移、翻译或覆盖29份恢复artifact。

### B. 本地文章阅读契约

- 在现有应用上显式开启本地文章能力；默认公开启动不注册私有API，公开MCP六工具仍只读公开知识。
- 本地文章模式不要求已有公开知识库：未配置公共DB时不注册公开查询/MCP，不创建伪release。客户端按明确的两个能力布尔值选择文章库或公开bootstrap；已显式配置却损坏的公共DB仍报错，不静默fallback。
- 本地能力只允许loopback绑定；私有HTTP处理还检查实际连接peer为loopback，不信任转发头。失败不降级成公开全文服务。不增加登录平台或第二服务。
- 页面新增“文章库”，既有article知识明确标“文章解读”；复用页面样式、导航和React文本转义，不重新设计网站，不引入Markdown/富文本依赖。
- 列表查询的q可为空，非空最多512字符；source仅wechat/rss/全部；limit默认20、1–100，offset为非负整数，布尔值不是整数。标题/原文/已有译文按字面子串搜索，ASCII英文忽略大小写，过滤在分页前。
- 来源身份为source+数据库record_id，不能用截断URL hash跨来源猜测。列表返回必要元数据和原文/译文可用标记，不携带全文；详情显式读取正文和已有译文。
- 所有记录均可列出，缺正文显示缺失；按采集时间、来源、record_id稳定排序，未知时间排后。不以长度、Layer1/2、ingestion或accepted过滤本地阅读。
- 每个响应绑定同一输入快照ID；该ID来自管理员提供的镜像receipt及文件hash核对。每次操作将同一已提升目录中的SQLite与receipt一起解析；目录内只读，镜像更新沿现有原子目录/链接提升方式，首版offset，无cursor平台。
- 新snapshot首次核hash并仅缓存一份已验证元数据，私有UI发现ID变化就清旧列表/详情并重读，不要求人工重启。镜像被原地修改而receipt未变化、或操作前后stat指纹变化时返回snapshot_changed，不把新数据贴旧hash；不能承诺直接读取活跃写库的跨页快照。时间未知不强造UTC。
- 私有页面只在运行时获取数据，不prerender全文进站点包；公开SQLite、HTML/JS及MCP中必须无私有sentinel。

### C. ingestion与显式重试

- 初始化压力先测实际分配阶段、版本和宿主机余量，再选最小修复。不能把外层timeout、降并发或再次加阈值单独当根因修复；合法资源配置修正允许，但须证明完整批次和下一次原调度可运行。
- 用户于2026-10-02另行明确批准必要内存扩容，已允许经备份与实测余量核对将MemoryHigh/MemoryMax提高至5/6 GiB；此授权取代本条原硬上限保持约束。业务provider、Vision及删除式prestart仍保持原合同；容量配置不代替完整批次与下一调度证据。若证据指向prestart，先记录新事实并重定范围。
- 失败重入增加一个明确的retry_requested整数标记（0/1，默认0）；保留failed状态和版本含义，避免负版本、假skipped状态或删除记录来“解锁”。
- reconcile仅对自己确认的假成功、在现有范围和auto-patch授权下置failed+retry_requested=1；普通failed保持隔离。实际正文尝试开始前原子消费标记，初始化失败不消费；再次失败不会每tick无限重入。
- 新字段按幂等迁移先部署，保留ID/字段/唯一约束；schema与fixture同步，正常ok/skipped的排除、来源隔离继续生效。258条历史failed不自动全部重放。

### D. 信息源

- 默认RSS沿当前active名单；对需保留的失效源逐项定位证书/解析/URL/超时，复用现有fetch/scraper，不关闭TLS验证、不新增fallback或主动换生产访问路径。
- RSS汇总保留计数，成功/部分失败/全部失败分别报告；部分失败使用非零退出供既有运维合同辨识。正文补抓最多一次/候选/当前运行，失败记录原因；不加入新队列或无限重试。
- 用户本轮已选择“先保持预算，修复轮转覆盖”。公众号目标使用明确的运行名单，先核当前配置49与DB58差异；名单不复制进源码或模型提示词。保持现行周期与20号×最多2页的单次上限，替换历史成功Top20筛选。
- 公众号新增last_attempted_at记录真实请求尝试；最久未尝试优先，零历史ok可选，失败不占据永远靠前的位置。last_scanned_at只记录成功（包括零新增），既有成功语义不改变。
- 覆盖验收是每run无重复、约定周期内全部目标至少有一次尝试。两页的文章时间窗不足时按最旧返回时间与上次成功时间报告coverage_gap；初次/未知时间记unknown，不自动多抓页或把账号覆盖称为全部文章无遗漏。
- 如用户选择每日扫描，须在执行前明确日调用预算和覆盖周期；默认方案不自动扩大付费调用。遇到额度/登录/限流，仅使用既有处理和停止合同。

### E. 存储副本与Wiki

- 不继续以缺ID差集宣称完整同步；也不根据目标多余ID直接删除历史集合。
- 先通过一个只读决策票确认源权威、实际consumer绑定、原生快照能力、空间和静止窗口。默认路线是**一次完整同版候选快照**：SQLite、graph/KV/chunks和原生Qdrant快照同窗取得，新目录/新集合恢复，保留原目标。
- 候选先验证身份、引用闭包以及新增/修改/删除语义。仅在已有配置可准确绑定候选并有回滚时受控提升；绑定不支持或数据归属不清则该分支BLOCKED，不恢复覆盖旧集合。周期完整快照先测成本，实证过高再设计增量，不先建watermark/tombstone服务。
- Wiki复用现有suggestion JSON、source-aware hydration、evolution worker和compiler；先隔离一条，再实质应用一条，初次试运行limit=1。来源缺source或引用无法解析时保持待核。
- worker源码docstring与实际写入可能不同，以实际调用及state/页面hash为准；CLI dry-run不调用模型。额度/失败沿当前provider合同，不恢复已失败的Codex coder路线或替换业务模型。
- Wiki日程使用已有worker入口；先手工成功，再由后续统一调度调用，不新增第二知识编排系统，也不全量bootstrap134条。
- 新公开Wiki默认使用既有producer的Wiki stage，消费已接受article；遗留evolution用于显式恢复的存量/仍有consumer的旧Wiki维护，同批同主题不再让两条路线重复生成。旧worker的一条成功不代表134条建议均获处理；未安排常态旧Wiki维护时该旧队列仍记partial。

### F. 已存正文→新知识→发布

- 现有生产入口只标准化HTML；增加显式stored-markdown输入分支，保留真正原始正文hash与来源表/ID/快照身份，不能包装为HTML后伪称原网页capture。
- stored-markdown以空行分段生成paragraph locator；code/原始字串不丢弃，未知原采集时间保留null，不用packet生成时间补造。既有HTML分支与hash/path控制保持原样；首片不发布输入图片。
- 新输入仍调用现有文章stage、引用校验、跨来源Wiki stage与五集合合并。每次一至两源；Hermes最终prompt的32KiB上限仍有效，超限明确待拆段，不静默截断，也不全量重跑历史加工。
- 跨来源Wiki须有不同的稳定来源身份及不同来源URL；同一文章在两表出现、同源两修订不能凑两来源。新增分支同时补这个现有producer的接受检查，沿现有规范化来源映射，不另建实体解析平台。
- 已审旧知识沿现有B2/B3票重放；新生产沿现有producer接受合同。结构接受与语义样本验收分别报告，不强加每次日更人工逐条审批，也不宣称字面quote校验能够证明全部事实。
- 保留原生usage与失败receipt；缺值是unknown/null，真实路由依执行证据。不复制输入全文/模型轨迹到公开包。
- 公开发布沿既有builder和单云票；首次手工候选→验证→提升，随后08:00加入一个既有调度。源码外的一个小批次receipt记录source hash、已接受输出、阶段结果和已服务release，复用不重算；无通用workflow平台。
- 发布准备在07:00 Asia/Shanghai开始，08:00只提升已准备并验证的候选；当时未准备好继续前版，不将08:00开始长模型任务后延迟发布称为准点成功。镜像刷新并入准备阶段，不把现行Hermes 05:00 UTC拉取误当08:00中国时间之前已刷新。

## Testing Decisions

主要用户验收接缝是“来源身份→本地只读HTTP→实际页面”，知识支线再延伸到“accepted→release→HTTP/MCP”；不按每个辅助函数建测试矩阵。

| 接缝 | 最小红例与绿门 |
| --- | --- |
| 本地阅读 | 同时含failed/无ingestion/Layer2 reject/缺正文及同ID异来源的临时SQLite；全部元数据可分页到达，原文/译文详情正确，默认公开模式404且包无private sentinel |
| 失败重入 | reconcile假成功→一次retry请求→候选→消费→失败不再自动重入；未申请failed和ok仍排除 |
| 初始化 | 实测初始化阶段资源证据；逻辑修改才加对应离线回归，真实批次与下一timer退出作为运行门 |
| 来源 | 部分源失败汇总正确、零新增扫描可对账、无历史ok账号可进入且失败能轮转；正文一旧一新持久化→Layer2 |
| 存储/Wiki | 新快照候选引用闭包及增/改/删；一建议产生有来源的正文变化、state回执和幂等 |
| 生产/发布 | Markdown精确引用与真实hash；HTML不回归；一新来源本地可读→accepted，另源形成Wiki；同版HTTP/MCP及失败保前版 |

沿现有pytest、CLI、TestClient与确定性Playwright harness；仅改动相关检查。未来真实浏览器须先有预览，停止的preview不算代码故障。本轮只文档，以上测试尚未执行。

## Out of Scope

新数据库/向量服务、图算法替换、embedding升级、全图语义重建、全量再抓/翻译、自动删除历史目标数据、登录/审核平台、Prefect/Redis/新Agent运行时；全量图片与缺正文恢复、BYOLLM最终能力、PC单写及旧链退役继续由已有父票完成，不能随本阶段默默取消或宣称完成。
